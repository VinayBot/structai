# Observability

Three independent surfaces: structured JSON logs, an in-process trace ring buffer, and Prometheus metrics. None of them require any external service to run — everything here is self-hosted in the API process itself.

## 1. Tracing

**File:** `app/core/tracing.py`.

`Span` is a plain dataclass: `span_id`, `trace_id`, `parent_span_id`, `name`, `start_time`, `end_time`, `duration_ms`, `status` (`"ok"` / `"error"`), `error`, `attributes: dict`.

`Tracer` holds a `deque[Span](maxlen=500)` — a fixed-size ring buffer, so the oldest spans are silently dropped once 500 accumulate. `get_tracer()` returns a process-wide singleton via `@lru_cache`.

`start_span(name, **attributes)` is an `@asynccontextmanager`:
- `trace_id` is read from the same `request_id_ctx` ContextVar the logging middleware sets per-request (falls back to a fresh id if unset, e.g. outside a request).
- `parent_span_id` comes from a second ContextVar (`_current_span_id`), so nested `start_span` calls automatically link child → parent and restore the previous span id on exit (a real stack, not just a flat list).
- On a raised exception inside the `async with` block, the span is marked `status="error"` with `error=str(exc)` and the exception re-raises — tracing never swallows an error.
- `duration_ms` is computed from the same clock on entry/exit and the span is appended to the ring buffer in a `finally`, so even an error path records its span.

**The only spans actually produced today** come from `app/services/structured_service.py::run_structured_loop()`:
- `structured.loop` (outer span) — attributes `tier`, `max_attempts`, and, set as the loop concludes, `outcome` (`"done"` or `"error"`) and `attempts`.
- `gateway.generate` (one per attempt, nested under `structured.loop`) — attributes `tier`, `attempt`, and, after the call returns, `provider`/`model`.

No other route or service creates spans — tracing coverage is narrow by design, scoped to the one request path (`/api/v1/structured/answer(+stream)`) where "how many attempts, which provider, how long" is the most useful to see.

### `GET /api/v1/traces`

`app/routes/traces.py` — auth required, `limit` query param (1–500, default 50). Returns `tracer.recent(limit)`, most-recent-first. This is a **global buffer, not scoped per user** — any authenticated user can see spans generated by any other user's requests. Fine for a demo/single-operator deployment; would need per-user filtering before this could ship as a multi-tenant feature.

## 2. Metrics

**File:** `app/core/metrics.py` — real `prometheus_client` usage (`Counter`/`Histogram`, `generate_latest()` + `CONTENT_TYPE_LATEST`), not a hand-rolled format.

| Metric | Type | Labels | Incremented in |
|---|---|---|---|
| `structai_http_requests_total` | Counter | `method`, `path`, `status_code` | `app/core/middleware.py::metrics_middleware` — every request |
| `structai_http_request_duration_seconds` | Histogram | `method`, `path` | same middleware |
| `structai_structured_answer_attempts` | Histogram (buckets 1–5) | — | `structured_service.py`, once per successful structured answer, with the attempt number it took |
| `structai_structured_answer_failures_total` | Counter | `reason` (`gateway_error`, `invalid_output`) | `structured_service.py::run_structured_loop()` — once per run that ends without a usable result, on the two previously-uninstrumented exit paths |
| `structai_output_leak_blocks_total` | Counter | — | same loop, when the output-leak heuristic trips |
| `structai_output_pii_blocks_total` | Counter | — | same loop, when `PII_MODE=block` and the output contains PII |
| `structai_gateway_calls_total` | Counter | `provider`, `model`, `outcome` | `app/gateway/router.py` — once per individual provider call attempt |
| `structai_guardrail_blocks_total` | Counter | `reason` | `app/routes/structured.py` — `reason="injection"` when the prompt-injection screen trips |
| `structai_rate_limit_hits_total` | Counter | — | `app/core/deps.py::enforce_rate_limit` |

`path` is the registered route template (e.g. `/api/v1/chats/{chat_id}`), not the raw URL — pulled from `request.scope["route"].path`, so metrics don't explode into one series per distinct chat id.

Plus whatever `prometheus_client` emits by default for the process (GC, memory, Python/platform info) — those show up in the same `/metrics` output.

### `GET /metrics`

`app/routes/metrics.py` — **no auth**, by Prometheus convention (a scraper has no bearer token). Returns `generate_latest()` as `text/plain; version=0.0.4; charset=utf-8`, not JSON.

### `GET /metrics/summary`

Auth required. `app/services/metrics_service.py::build_summary()` aggregates the above into one JSON document for the frontend's Metrics tab. Two accounting decisions worth knowing:

- `totals.errors` / `totals.error_rate` count **5xx responses only** — genuine server failures. Routine 4xx traffic (401 on an expired/missing token, 404, 422, 429 from the rate limiter) is reported separately as `totals.client_errors`, so it no longer inflates "Errors". `by_endpoint[].error_count` uses the same 5xx-only definition for consistency. The per-status donut (`by_status`) is unaffected — it already buckets 2xx/4xx/5xx independently.
- `failed_runs` (`{total, by_reason}`) tracks structured-answer runs that ended without a usable result — `gateway_error` and `invalid_output` (both from the new `structai_structured_answer_failures_total{reason}` counter) plus `output_leak` and `output_pii` (from the two counters above). This is the metric that actually matters for `POST /api/v1/structured/answer/stream`: that endpoint is a `StreamingResponse` that always answers HTTP 200 regardless of outcome (the terminal SSE event — `done`/`error`/`output_leak`/`output_pii` — carries the real result), so HTTP-status accounting alone can never see a failed streamed run. `failed_runs` is the only place that failure becomes visible.
- `totals`, `by_endpoint`, and `by_status` are all computed over the same trailing 60-minute window the timeseries chart uses (`RequestRingBuffer.recent(since_ts=...)`), so the headline tiles and the chart beneath them describe the same period instead of silently disagreeing (previously the tiles read the full 5000-entry buffer).

## 3. Structured logging

**File:** `app/core/logging.py`.

`configure_logging()` installs one `StreamHandler(sys.stdout)` on the root logger with a `JsonFormatter` and a `RequestIdFilter`. Every log line is a JSON object:

```json
{"level": "INFO", "logger": "app.services.structured_service", "message": "...", "request_id": "a1b2c3d4e5f6a7b8"}
```

Plus `exc_info` (formatted traceback) when logging an exception. `request_id` comes from the same `request_id_ctx` ContextVar tracing uses, set per-request by `request_id_middleware` (which also honors an incoming `X-Request-Id` header, or mints one via `new_request_id()`, and echoes it back on the response).

**Known gap:** there's no timestamp field — `JsonFormatter.format()` never reads `record.created`. Reconstructing a timeline from logs alone currently relies on stdout's own arrival order (or an external collector stamping its own receipt time), not a field in the log line itself.

**Confirmed:** nothing in `app/routes/*.py` or `app/services/*.py` calls `logging.getLogger()` directly — the only call site in `app/` is inside `configure_logging()` itself. Combined with PII redaction running before the prompt reaches the model (see [GUARDRAILS.md](GUARDRAILS.md#2-pii-redaction)), raw prompt/response content never reaches a log line, consistent with the project rule to never log raw prompts or secrets.

## 4. Health & readiness

**File:** `app/routes/health.py`. No auth on either.

- `GET /health` → `{"status": "ok"}` unconditionally — a liveness probe that only confirms the process is up and routing requests.
- `GET /ready` → `{"ready": <bool>, "db": <bool>}`, both mirroring `app.db.ping_db()` — a readiness probe that actually checks the database connection. A DB outage surfaces as `{"ready": false, "db": false}` with a normal `200`, not an HTTP error — callers (e.g. an orchestrator's readiness check) are expected to read the body, not just the status code.

## Known limitations

- No timestamp field in JSON log lines.
- `failed_runs` only covers the structured-answer loop (the one place a run can "fail" without an HTTP error status). Other routes have no equivalent outcome-level counter — a 2xx response there is assumed to mean success.
- Chat-message persistence (direct message writes, and the MCP `send_message` tool) skips PII redaction — see [GUARDRAILS.md](GUARDRAILS.md#2-pii-redaction). Only `/api/v1/structured/answer(+stream)` is covered, via the shared `guard_prompt()` helper.
- `/api/v1/traces` is a single global ring buffer, unscoped per user, capped at 500 spans (oldest silently evicted).
- Tracing coverage is narrow: only the structured-answer path (`structured.loop` / `gateway.generate`) produces spans — chat/project CRUD and auth are untraced.
- `/metrics` and `/api/v1/traces` are both in-process/per-instance — nothing aggregates across multiple API replicas.
